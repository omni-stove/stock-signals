# stock-signals

半導体まわりの日本株を対象にした、ニュース駆動のスイング売買シグナル生成システム。
公式IR・ニュース・適時開示・株価などを自動で収集し、銘柄ごとの「生きたコンテキスト」を育てながら、
**buy/sell 判定**を Slack に流し続ける。取引自体は手動で、本リポは「売買判断の材料を非同期で
並べ続ける装置」。対象は数日〜3週間保有のスイング。

## セットアップ

```sh
make setup
```

その後 `worker/.dev.vars` に実値を埋める。

## 全体構成

収集は Cloudflare Worker、判定は GitHub Actions 上の Claude Code(LLM)で
完結する完全クラウド構成。Worker が cron で集めた新規データを起点に、
`context-builder` → `signal-judge` の2段が `repository_dispatch` で連鎖する。

```mermaid
flowchart LR
    EXT["外部データソース<br/>IR・ニュース・適時開示・株価・市場"]
    CLOUD["☁️ Cloudflare Worker<br/>収集<br/>自動でデータを集めて保存"]
    GHA["⚙️ GitHub Actions<br/>判定 (LLM)<br/>集まったデータから buy/sell を判定"]
    SLACK["Slack<br/>判定・地合い・通知が届く<br/>ユーザーが叩く接点"]

    EXT --> CLOUD
    CLOUD -->|新規データで起動| GHA
    GHA -->|判定を投稿| SLACK
    SLACK -.->|コマンド / 返信| CLOUD
```

この図は3環境の流れだけを示す。各部の設計判断は後述の「構成思想」、
実装の詳細(テーブル構成・エンドポイント・skill の入出力)はコードが真のソース。

上の図は**ユーザーが何もせず自動で受け取るもの**: 寄り前の地合い、新着データを起点にした
buy/sell 判定、コンテキスト更新、新規IR通知。これらは Worker の cron / dispatch で勝手に流れる。
**ユーザーが Slack から能動的に叩けるもの**は後述の「Slack からの能動操作」を参照。

### Slack に流れてくるもの (自動)

ユーザーが何もせず自動で Slack に届く出力は次の6種類。

- **判定**: buy/sell の方向 + 売買線 (now / 支持線待ち wait@line) + 損切り/リスクリワード + 根拠が
  1行流れる。動詞 (利確/増し玉 等) は付けず、方向と値だけ出す — 保有有無に応じた使い方は読み手に委ねる。
  根拠には判定の核になった「直近の重大トピック」が引用される。該当があれば末尾に強制フロー観測
  (追証売り/踏み上げ) と指数リバランス窓が観測事実として相乗りする (判定とは独立)。
- **地合い**: 寄り前に `リスクオン / 中立 / リスクオフ` + 当日の売買可否 (`拾い場 / 様子見 / 守り`) を
  1本出す。個別 buy/sell の前に「今日エントリーしてよい地合いか」を見るゲート。前夜の米指数・日経先物 (寄り前)
  と場中に同時進行で動くアジア指数 (日経225・KOSPI の現値)・セクター動向に加え、保有銘柄ページに載らない
  市場テーマ見出し (半導体/AI/金利/米国市場/市況) を材料に読む。米国休場明けの朝は前夜の米指数が
  「前営業日に日本市場が消化済みの持ち越し値」だと判定側が識別し、新しい材料としては扱わない。
- **コンテキスト更新**: context-builder が銘柄コンテキストを育てるたび、更新後の全文をセクション
  ごとに区切ってコンテキスト更新チャンネルに投稿する (判定チャンネルとは分離)。コンテキストの育ちを覗く窓。
- **新規IR**: 新着IRを通知する。判定とは別チャンネルに分けることもできる。
- **新規ニュース**: 新着の銘柄ニュース・市場テーマニュース (半導体/AI/金利/米国市場/市況) の見出しを通知する。
  IR・判定とは別のニュース専用チャンネルに分けることもできる (未設定なら通知しない)。
- **イベントリマインダー**: 重要イベント (監視銘柄の決算発表 / FOMC / 日銀会合 / 海外ピア決算 /
  SQ / 指数リバランス) の 3日前・前日・当日の朝に予告を1本流す。該当がない朝は流れない。
  専用チャンネルに分けることもできる (未設定なら判定と同じチャンネル)。
- **収集異常の警告**: 収集元ページが取得できているのに記事一覧が 0 件しかパースできない状態
  (= サイト側の構造変更で収集が静かに止まっている疑い) を検知すると、朝夕の収集時に警告を1本流す。

### Slack からの能動操作

ユーザーが Slack から能動的に叩けるのは次の通り(コマンドは引数なしなら銘柄ピッカーが出る)。

| 操作 | できること |
| ---- | ---- |
| `/signal [銘柄]`     | 任意のタイミングで buy/sell 判定を出す(自動判定と同じ skill を手動起動) |
| `/crash [銘柄]`      | 暴落プリモーテム。崩れる道筋を銘柄固有/マクロの両面で3〜5本列挙するリスク棚卸し |
| `/context [銘柄]`    | その銘柄の保存済み living context 全文を context チャンネル(`SLACK_CONTEXT_CHANNEL`)へ流す。解析は走らず D1 の保存結果を表示するだけ |
| `/position`          | 保有建玉を登録する(Slack ユーザー単位)。平均建値・株数を直接上書きする。スレッド返信時に本人の含み損益として効き、引け後のポジション評価 DM の対象になる。株数 0 で手仕舞い |
| `/trade`             | 約定 1 回(買い増し / 部分決済)を既存建玉に反映する。増しは加重平均で平均建値を再計算、減らしは平均建値据え置きで株数だけ減算(0 株で手仕舞い)。対象が無い増しは新規建玉になる |
| `/profile`           | 好み・特記事項(リスク許容度/保有スタイル/最大ポジション率/投資余力(現金残高)/メモ)を登録する(Slack ユーザー単位)。スレッド返信時に本人の売買スタイルとして効く |
| `/portfolio`         | 全建玉+現金を 1 画面で一括編集する。現在の建玉が `コード 現物\|信用 買\|売 建値 株数` の 1 行 1 建玉で prefill され、本文を書き換えて一括保存(行を消す=手仕舞い / 値を書き換える=更新 / 行を足す=新規)。保存時に本人の建玉を丸ごと置換する。銘柄ごとに `/position` `/trade` を開き直さず一度にまとめて直したいとき用 |
| `/mystatus`          | 登録済みのプロフィールと全保有建玉(建玉金額・含み損益(円/%)付き)、信用建玉があれば委託保証金維持率と追証ライン(20%到達までの評価損余力)を本人にだけ表示する。追証は現金残高+現物の代用評価(現値×80%)+評価損益からの概算。`/position` `/profile` の確認用で、登録は変えない |
| 解析投稿にスレッド返信 | 同じスレッドで Claude と対話する。コンテキスト+数値+本人の建玉と好みを読んで答える |

### 監視銘柄の追加・削除

`update-tickers` skill を手で叩く(`add <code>` / `remove <code>`)。追加後は通常の cron / workflow が
その銘柄のデータを拾い始める。削除は watchlist から外すだけ(収集済みの D1 データはそのまま残す)。

### LLM連鎖 (新規データ検知 → Slack)

ここまでの自動出力を生む内部配管。Worker が新規 IR/ニュース/開示/レーティングを検知すると、
`context-builder`(銘柄コンテキストを更新)→ `signal-judge`(buy/sell を判定)が dispatch で
連鎖し、Slack に流れる。スレッド返信には `slack-reply` が同じスレッドへ返答する。各段の入出力は
workflow / skill が真のソース。

### Cron スケジュール

収集 (Worker) は JST 基準で寄り前・場中5分毎・引け後に走る(東証が開かない土日はスキップ)。
地合いの `market-check` は寄り前に出し、個別 buy/sell の前段ゲートとして先に届く。
引け後には、その日の最新 buy/sell 判定と各ユーザーの建玉 (建値・含み損益・順行/逆行) を読んだ
**ポジション評価**を本人へ DM する。判定 (方向) は signal-judge が銘柄ごとに出し、建玉への読み替え
(継続/増し玉/一部利確/損切り検討と急ぎ度、ポートフォリオ全体の所見) はユーザーごとに 1 ジョブで
LLM が行う (GitHub Actions の position-review、ユーザーは直列)。
具体的な cron 式と種別ごとの収集内容は Worker の設定が真のソース。

## 構成思想

全体像を踏まえた上での、各部の設計判断。

- **決定論的な前処理はすべて Worker に寄せる**。記事・株価・ファンダ・適時開示・レーティングの取得・正規化は Worker が担い、LLM 判定は集まった材料を読むだけにする。
- **判定は2段に分離**。前段 `context-builder` が銘柄ごとの生きたコンテキスト(経営判断・商品ラインナップ・技術ロードマップ + 直近の重大トピック)を育て、後段 `signal-judge` がそのコンテキスト+価格/地合いを読んで buy/sell を判定する。
- **判定は必ず buy か sell の2値**。薄い材料でも片側に倒す。方向に売買線 (現値で約定するなら now、現値直下の支持線待ちなら wait@line) と損切り/リスクリワードを添える。利確/増し玉 等の動詞は付けない — 相場の向きと水準を出す係で、保有有無に当てた解釈は読み手の領分。
- **記事系は1つに合流**。公式IR・銘柄ニュース・適時開示(TDnet)・証券会社レーティングはすべて同じ記事ストアに集約し、収集元が増えても判定側は無改修で読む。銘柄に紐付かない市場テーマニュースだけは別ストアに分け、地合い判定 (`market-check`) が読む。ただし市場テーマ見出しに監視銘柄の名前・別名・製品ワードの言及があれば、その銘柄の個別判定も起動する。
- **判定は地合いを潜らせる**。`market-check` が市場全体の地合い(リスクオン/中立/リスクオフ)を寄り前に1本決め、当日の個別 buy/sell はそれを潜って出る — **リスクオフの日は買い線が下方修正されず損切りが固められ、現値以上を追う水準が封じられる**。
- **判定本文に観測事実を相乗り**。強制フロー(追証売り/踏み上げ)とスケジュール型イベント(FOMC/日銀/SOX系ピア決算)を、方向判断とは別の観測事実として判定に織り込む。

## ディレクトリ構成

| パス | 中身 |
| ---- | ---- |
| `worker/`            | Cloudflare Worker (収集) |
| `.github/workflows/` | LLM判定の Actions(market-check / context-builder / signal-judge / crash-scenario / slack-reply / position-review)・CI・デプロイ。判定ルールは各ワークフローの prompt にベタ書きし、数値コンテキストは `@` でファイルから取り込む |
| `agents/skills/`     | 手動運用の Claude Code skill(`update-tickers` ほか。`.claude/skills/` は symlink) |
| `scripts/`           | Slack 投稿整形・判定 dispatch・手動ツール・品質ゲート(`verify.sh` 等) |
| `config/`            | sources / events / peers の人間向け設定。銘柄一覧の真ソースは `worker/src/lib/watchlist.ts` の `TICKERS` |

> Slack App の登録・Worker / GitHub Actions の secret 設定といった構築手順は、利用ではなく
> セットアップの領域なのでワークフロー (`.github/workflows/`) を参照。
